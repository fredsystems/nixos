## Part 0 -- Live secret exposures

These changed the recommended priority order, so they lead.

### S1: Attic write token committed in a public repository

`gh repo view --json visibility` returns:

```json
{ "isPrivate": false, "visibility": "PUBLIC", "nameWithOwner": "fredsystems/nixos" }
```

A bare Attic JWT is hardcoded in five places:

| File | Lines |
| --- | --- |
| `.github/workflows/ci-linux.yaml` | 403, 471, 637 |
| `.github/workflows/ci-darwin.yaml` | 311, 458 |

Decoded payload (token value itself deliberately not reproduced here):

```text
sub    = fred
nbf    = 2026-01-27 19:28:09 UTC
exp    = 2038-01-27 19:28:09 UTC          <- 12-year lifetime
claims = {"https://jwt.attic.rs/v1":{"caches":{"fred":{"r":1,"w":1,"cc":1}}}}
```

`w:1` plus `cc:1` grants **write and create-cache** on the `fred` cache.

Why this is more than cache abuse: every host trusts that cache's signing key
as a substituter (`modules/base/system.nix`), and Attic signs content with the
cache's real key on ingest. Anyone who can read this public repo and reach
`192.168.31.14:8080` can push an arbitrary store path that the entire fleet
will accept as trusted and substitute. That is a fleet-wide supply-chain write
primitive. LAN-only reachability narrows the blast radius but does not remove
it, particularly since `sdrhub` advertises `192.168.31.0/24` over Tailscale.

The token is burned and is in git history. It requires **revocation and
reissue**, then `secrets.ATTIC_TOKEN`. Relocating it without revoking the old
one achieves nothing.

### S2: Grafana secret_key hardcoded in the same public repository

`modules/monitoring/master/grafana.nix:74`:

```nix
secret_key = "SW2YcwTIb9zpOOhoPsMm"; # default from pre 26.05. Why we removed it I'll never know.
```

To answer the in-line comment: it was removed from nixpkgs precisely because
shipping a publicly known default for the value that signs Grafana's auth
cookies is a vulnerability. Anyone reading this repo can forge a session.

Also burned, also in history -- rotate, do not merely relocate. The fix is a
copy of the `admin_password` pattern six lines above (`sops.secrets` plus
`$__file{...}`).

## Part 1 -- opencode.jsonc

Resolved. The problem was not formatting; the file was schema-invalid, which
is why it silently failed to load.

Per `https://opencode.ai/config.json`, `command` is shaped:

```jsonc
"command": {
  "<name>": {
    "template": "...",  // REQUIRED
    "description": "...", "agent": "...", "model": "...",
    "variant": "...", "subtask": false
  }
}
// additionalProperties: false
```

The file contained `command.agent.{general,explore}`. opencode parsed that as
a command literally named `agent`, missing the required `template` and
carrying two unknown keys. `Config.additionalProperties` is `false`, so this
is a hard `ConfigInvalidError` -- no config loaded at all.

Agent overrides belong under the **top-level** `agent` key, where `general`
and `explore` are explicitly named built-ins in the schema. Corrected.

Non-issues ruled out along the way:

| Check | Result |
| --- | --- |
| Comments and trailing commas | Legal; schema sets `allowComments: true`, `allowTrailingCommas: true` |
| `prettier 3.8.3 --list-different` | Clean, exit 0 |
| `skills.paths` shape | Correct (`{paths: string[], urls: string[]}`) |
| `opencode/claude-sonnet-5` model id | Valid per models.dev |
| `instructions: ["agents.md"]` | Target exists |
| Git state | Broken block was uncommitted local cruft; HEAD never had it |

## Part 4 -- CVE scan root cause

### Why it is failing now

Identical signature on both recent failures (`gh run view 30806645765
--log-failed` and `30968134758`):

```text
##[error]grype output has no .vulnerabilities key
##[error]Process completed with exit code 1.
```

That is the repo's own guard at `cve-scan.yaml:207-214` firing correctly. It
fires for all seven scanned systems on both the 2026-08-03 scheduled run and
the 2026-08-05 manual retry.

Run history:

| Date (UTC) | Event | Conclusion |
| --- | --- | --- |
| 2026-08-05 | workflow_dispatch | failure |
| 2026-08-03 | schedule | failure |
| 2026-07-27 | schedule | success, 96-176 CVEs per system |
| 2026-07-06 | schedule | failure, same signature, self-resolved by 07-13 |
| 2026-05-04 to 2026-07-20 | schedule / dispatch | all success |

Ruled out by direct checking rather than assumption:

- **Not a grype version bump.** The `grype-0.115.0` store path is identical
  in the last green run and both red runs.
- **Not a workflow change.** Last substantive edit to `cve-scan.yaml` was
  `4cedcdc6` on 2026-07-08, already green for two weeks afterward. The
  2026-08-03 commit `146ed6a8` only adds a fork guard, a no-op for
  `schedule` and `workflow_dispatch`.
- **Not the nixpkgs bump.** The failing run's own drvPath shows it evaluated
  against the pre-bump `nixpkgs-stable` revision; the bump PR merged after.
- **grype did not crash.** No panic, no non-zero exit before the guard.

What actually happened: match counts fell from a stable 96-176 per system
every week since May to **zero, uniformly, across seven unrelated closures,
on two invocations two days apart**. When grype's match slice is empty, its
CycloneDX writer emits a `nil` Go slice and `omitempty` drops the key
entirely instead of writing `[]`. Same bug class as `anchore/grype#1759`. The
comment at `cve-scan.yaml:203-206` anticipated exactly this.

The upstream trigger is a grype vulnerability-DB problem: either a stale or
corrupt persistent cache under `$HOME/.cache/grype/db` on the long-lived
self-hosted runners, or a transient gap in Anchore's NVD provider data.

**This is the one item not verifiable from outside the runner.** Run
`grype db status` on the runner to distinguish the two.

### Why the ancient CVEs appear

The suspicion that these are false positives is correct, and the mechanism is
confirmed against live data rather than theorized. Rolling issue #1717
currently lists, among others:

| CVSS | Package | CVE | NVD CPE configuration |
| --- | --- | --- | --- |
| 8.8 | `cups-2.4.19` | CVE-2018-6553 | `cpe:2.3:a:cups:cups:-:*:*:*:*:*:*:*` |
| 8.8 | `graphite2-1.3.15` | CVE-2017-5436 | `cpe:2.3:a:sil:graphite2:-:*:*:*:*:*:*:*` |

The version field is literally `-`, the CPE "not applicable" placeholder,
with **no `versionEndExcluding` or `versionEndIncluding` anywhere**.
CVE-2018-6553's real scope was Ubuntu vendor-patch versions
(`< 2.2.7-1ubuntu2.1`), which do not map onto upstream cups versions at all,
so NVD shipped an unbounded product-level CPE. It matches every cups version
that will ever exist. CVE-2017-5436 has the identical shape.

Two important consequences:

1. The migration off `vulnix` (documented at `cve-scan.yaml:23-35`, measured
   1380 to 160 entries) fixed the **product-name-collision** class. It
   structurally **cannot** fix this class, because the defect lives in NVD's
   own CPE dictionary, which every CPE-based scanner consumes verbatim.
2. Both examples are **CVSS 8.8**, so a severity floor would not have
   suppressed either. That is the intuitive fix and it does not work here.

Currently no mitigation is applied at all: no `--whitelist`, no CVSS floor,
no publication-date filter, and `meta.knownVulnerabilities` is not consulted.

### Recommended CVE remediation, in order

1. **Add a canary component to the zero-match guard.** This is an
   independent correctness bug: today the workflow cannot distinguish "DB is
   dead" from "genuinely clean", and the `total == 0`-with-key-present
   variant would pass the guard untouched and **close the tracking issue with
   a false all-clear**. Inject a known-vulnerable CPE into the SBOM, or run
   `grype db check` as a preceding step.
2. **A checked-in `.grype.yaml` ignore list with per-entry reason and review
   date.** Best fit for this repo specifically, because
   `tracked-upstream-fixes.json` plus `track-upstream-fixes.yaml` is already
   exactly this culture: weekly checker, sticky issue, per-entry revert
   metadata. Auditable and git-blamable. Cost: real triage toil, roughly 14
   unique packages per week initially.
3. **A publication-date floor as a coarse pre-filter feeding item 2**, so the
   ignore list does not grow without bound. Only in combination with item 2,
   so a human still signs off rather than a blanket cutoff silently eating
   findings.
4. **`osv-scanner` as a scoped month-long parallel trial, not a swap.** OSV
   encodes precise per-ecosystem version ranges instead of CPE match strings,
   which eliminates this class outright. Honest cost: sbomnix emits
   structural CPEs, and 50-80 percent of every SBOM is Nix plumbing
   (`etc-fstab`, `X-Restart-Triggers-*`) with no OSV identity, so the trade
   is fewer false positives against possible silent coverage loss. Run both,
   diff for a month, then decide.

Leave the guard hard-failing and the findings report-only. That split
(`cve-scan.yaml:600-606`) is already correct. Closure scope is also already
correct -- it scans `system.build.toplevel`, not just flake packages.

## Part 7 -- Additional observations

These are not from the subagent reports.

1. **`flake.nix:69-74` is now factually wrong.** The comment says "The ref
   below is knowingly stale -- `nixos-25.11-small` stopped receiving commits
   on 2026-06-30 ... Do not bump it by hand before that PR lands." Line 78 is
   already `nixos-26.05-small`. The fix landed; the comment did not get
   removed. Since the block exists specifically to stop a human from
   hand-bumping, a stale copy will actively cause the wrong action next time.
2. **Nothing validates this repo's own opencode config.** The pre-commit
   stack already runs `check-jsonschema` for `check-github-workflows` and
   `check-github-actions`. Adding `opencode.jsonc` against
   `https://opencode.ai/config.json` is nearly free, and it would have caught
   the exact bug that opened this session at commit time rather than as a
   silently non-loading config. Strongest cheap win in this section.
3. **There is no secret-rotation story.** Two credentials are burned in
   public git history right now, and the process for rotating either is
   undocumented and unrehearsed. Given that `sops updatekeys` is already a
   manual runbook step, rotation is the weakest operational muscle here.
   Worth a real runbook.
4. **A backup without a tested restore is not a backup.** When restic lands,
   add a scheduled restore-verification job in the same change. Otherwise the
   flaw gets discovered during an actual incident. The `acarshub-db-repair.sh`
   script deleting a 5.6 GB stale backup with no replacement is a preview of
   that failure mode.
5. **The detection-versus-survivability asymmetry is the real headline.**
   This repo has alert-rule linting, a metric-existence checker,
   closure-based drift detection, and upstream-fix tracking. That is a more
   mature observability story than most professional fleets. But
   observability reports that the house is on fire; it cannot rebuild the
   house. Zero backups, no tested restore, and a fleet-wide cache-write
   credential in public git sit behind an excellent detection layer. Closing
   that asymmetry matters more than any individual item above.
6. **On the CVE instinct.** The suspicion that the ancient CVEs were false
   was correct, with a verified mechanism. The general form is worth
   internalizing: a CPE-based scanner cannot know that nixpkgs backported a
   patch, and NVD ships many CPEs with no upper version bound. Any tool in
   that family will keep doing this.
